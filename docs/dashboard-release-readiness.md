## Metric audit

| Metric | Data path and verified behavior | Data limitations |
| --- | --- | --- |
| Grain in bins | Farm-scoped, paginated `bins.current_bushels`, grouped by saved `crop_type`. The dashboard uses the same balance projection as Bins, including its capacity clamp, and flags when that projection differs from the raw row. Opening estimates, adjustments and ticket deductions use the existing grain commands. Deletion replays the affected bin ledger. Reassignment changes contract allocations only. | The system tracks the current crop label per bin, with Beans and Soybeans grouped in the dashboard. A bin can be relabeled over time. The system does not track multiple crops sharing one bin, or independently verify a physical quantity. Bin, ticket and contract reads are separate statements, so concurrent changes can cause a temporary snapshot discrepancy. |
| Storage utilization | The raw numerator and denominator use the same set of bins with finite, positive confirmed capacity and a valid balance. Confirmed empty bins count toward capacity. Partial coverage shows the included bin count. Raw above-capacity readings are flagged and the calculated number is retained when the affected bin is eligible. | The current schema only supplies `estimated_capacity_bushels`. Positive estimates alone do not establish confirmation. Real records show **Confirmed capacity needed** until a confirmation source is approved. The fictional adapter supplies confirmation for its three sample bins only. No physical crop-specific capacity is assumed. |
| Contract fulfillment | Contracts and the dashboard share the rollup of saved `CONTRACT` allocations by contract UUID. Each split contributes only its allocated bushels. Remaining is floored at zero. The ratio uses the saved contracted quantity and surfaces overdelivery or invalid quantities. A fully fulfilled contract with consistent data leaves Open Deliveries. | `contracted_bushels` is the current authorized quantity, including accepted amendments. There is no separate immutable original-quantity field or amendment history. The Westfield demo contract starts with **22,000 contracted, 0 applied, 22,000 remaining**. The denominator comes from the contract row. Existing commands reject increases beyond the allocated room and amendments below applied quantity, with their existing 0.01 bu tolerance. |
| Deadlines | An explicit single `YYYY-MM-DD` value in the existing delivery window is an exact saved day. Month-only windows remain as written. Deadline classification uses civil days in a known farm time zone, with 0–14 days marked Due soon and Overdue only after the exact day has passed and a balance remains. Largest remaining balance still sorts first. | The schema has a free-text window and lacks separate delivery start/end fields and a verified farm time zone. Historical ranges and month-only text require confirmation before conversion. The real route displays explicit saved days and windows, and suppresses warning states without a verified farm calendar. The isolated demo provides the calendar and one exact end date. |
| Payments to review | Counts current farm tickets marked `Not paid` or `Partially paid`. The combined History filter includes the same two statuses across all crop years. | This is a recorded workflow status. The release dashboard shows no amount owed. |
| Recent grain activity | The six latest eligible records from the past seven days by record time. Saved tickets use `tickets.created_at`. Supported bin changes use recorded before/after balance deltas and inventory transaction timestamps. Ticket sale transactions are excluded from the activity list to avoid repeating the saved ticket. | A ticket entered later appears at entry time, separate from delivery date. A deleted record is absent. Corrections and manual estimates remain subject to the existing ledger rules. |

## Verification and rollout

1. Review `20261112020325_contract_display_names.sql`. It adds one nullable column and length check. The isolated local PostgreSQL rehearsal applies the real migration after a legacy contract exists, checks missing and invalid aliases, exercises a split delivery, alias-only rename, reassignment, deletion, bin restoration and movement, and checks other-farm access. An approved disposable hosted staging rehearsal remains required before any production migration recommendation. Check legacy client writes, schema cache refresh, role grants, farm isolation, duplicate aliases, and data preservation there.
2. If numeric storage utilization and automatic deadlines are required at launch, agree on a capacity confirmation source and a per-farm IANA time zone. Use structured start and end dates if the product needs exact deadlines for ranges. Keep existing window text and confirm dates explicitly. No schema change for these items was applied or introduced here. A production rollout with safe unavailable states is a separate product decision.
3. After staging verification, release compatible API changes before the frontend and keep the additive alias column if frontend/backend artifacts roll back. The existing dashboard query without `grain_position=true` and existing contract and ticket endpoints retain their response shapes. The submitted iOS app has bundled assets and continues to use legacy screens. New UI requires a separately tested native build. Browser sizing on Windows does not verify native iPhone or iPad behavior.
4. The coordinated release still requires a combined candidate, regression and hosted acceptance, an approved transition for existing farms and iOS 1.0, reviewer access, and device validation and App Review approval for 1.1. Verify the StoreKit U.S. gate, including unknown and non-U.S. storefronts, the Safari handoff, and reviewer access on the actual archive. Confirm release distribution and applicable terms. The U.S. external-link rule is described in [Apple App Review Guidelines §3.1.1(a)](https://developer.apple.com/app-store/review/guidelines/#in-app-purchase). Keep paid presentation and enforcement disabled until separately authorized.

**Verdict.** Design E is suitable for local review and approved staging rehearsal with the documented data limitations. The combined paid release is NO-GO pending integration, hosted migration rehearsal, product decisions about incomplete data, and the native and rollout gates above.
