# Production billing and iOS 1.1 release procedure

## Prepared behavior

Monthly is $29.99/month, annual is $299.99/year, and the first eligible Stripe subscription has a full 30-day trial. Checkout uses fixed server price IDs. Production prices must be active recurring USD prices on the same product and must match those exact amounts and intervals. Trial days cannot be shortened through configuration.

Production mode pins Supabase project oxqsianyivqevtwzhdnq, the direct host db.oxqsianyivqevtwzhdnq.supabase.co or an explicitly configured Supabase session pooler, the dedicated binflow_billing_prod login and https://getbinflow.com/app/. PostgreSQL uses certificate validation, TLS 1.2 or later, a nonprivileged role and no connection-string TLS overrides. Runtime checks reject direct public-table access, Auth access and enforcement-write privileges, including inherited grants. Render needs the IPv4-compatible session pooler unless direct IPv4 connectivity is separately available. Copy the exact pooler host from the production Connect panel into BILLING_PRODUCTION_POOLER_HOST. Never infer the pooler index from the region. Its URL must use port 5432 and username binflow_billing_prod.oxqsianyivqevtwzhdnq. The host must match the explicit allowlist and Supabase domain pattern, and tenant, Auth keys and role remain pinned to production. No production pooler host has been guessed or configured.

Production requires live Stripe keys and live events. Local and staging modes require sandbox keys and sandbox events. The runtime verifies production prices and the dedicated portal configuration before accepting requests. It requires payment-method updates and cancellation, and requires portal plan changes disabled to preserve the full trial and avoid prorations. Webhooks verify the original raw request bytes and remain idempotent. Snapshots come from the canonical subscription list, so delayed or reordered event bodies cannot manufacture access.

An hourly, nonoverlapping process worker reconciles subscriptions and retries pending cancellation outbox entries. Request-time checks refresh stale or expired paid/trial entitlement before enforced access is denied. The billing status screen also refreshes aging snapshots. A suspended Free service cannot promise wall-clock scheduling, so production operations must schedule `npm run billing:reconcile` at least every six hours on an approved runner, observe its exit code and aggregate output, and alert on failures or missing runs. The startup worker and request recovery are additional protection. No hosted scheduler has been provisioned or configured.

## Old-client compatibility and access preservation

The submitted 1.0 app contains bundled assets and cannot render the billing page or handle a subscription 402. A version header cannot safely identify it or grant entitlement. There is no server-only fix for that UI.

There is one coordinated paid launch after physical-device testing, iOS 1.1 App Store approval, production readiness and owner authorization. Until then, both existing and new customers remain free and fully usable. Keep provider billing, customer-facing billing and database enforcement disabled in production. Do not show activation, price selection, Checkout or billing-management buttons to customers.

BILLING_CUSTOMER_UI_ENABLED defaults false and is checked separately from provider processing. The client only displays billing when the authenticated server entitlement explicitly permits it. Direct Checkout, portal, pricing and handoff routes also reject requests when billing is hidden. Browser handoff pages first obtain server permission and otherwise show an ordinary link into BinFlow. Query strings cannot expose pricing or initiate payment.

For isolated staging acceptance, testers may explicitly enable BILLING_ENABLED and BILLING_CUSTOMER_UI_ENABLED with sandbox credentials. Production additionally requires the database coordinated-launch approval, native and legacy-client approvals, and active enforcement. The UI and payment-creation permission stay hidden before the scheduled enforcement time, even if the server presentation flag is accidentally enabled early. Turning policy back to disabled hides purchasing again.

At the approved launch, the same database entitlement policy restricts unpaid new farms on web and iOS. Eligible U.S. admins can activate a 30-day trial using the existing website handoff. Employees use the farm's shared access and cannot purchase. Existing farms and remaining 1.0 installations require an explicitly reviewed transition with finite, audited access grants. A version header grants nothing. Native approval alone does not prove old installations upgraded.

The release gate defaults to denying enforcement. Scheduling enforcement requires the operator to record coordinated_launch_approved, native readiness and the legacy-client plan, a cutoff, reviewer, note and timestamp, and coverage for active farms at/before that cutoff at the proposed enforcement time. Existing subscriptions or explicit, unexpired grants provide coverage. Grants are never created automatically. Auth/service/runtime roles cannot authorize this gate or edit enforcement.

The owner must supply a reviewed manifest with farm UUID, kind (migration, review, demo or complimentary), start/end, reason and authorizer. Match UUIDs privately against the actual customer/reviewer inventory. Choose the duration explicitly. The existing access-grant constraint caps grants at 366 days and requires audit details. Avoid grants for farms merely because their names look like fixtures. Reviewer access must remain valid throughout review and allow normal functionality without a purchase.

## Rollback and operational checks

Before billing launch, the rollback revision must preserve the installed billing RPCs and policy. An older API that ignores enforcement is unsuitable once enforcement is active. Disable policy enforcement first with approved operator SQL, record the audit, then disable the handoff/provider operations or restore the compatible API/frontend artifact. Keep Stripe webhooks and reconciliation available for subscriptions already sold. Disabling provider operations does not cancel subscriptions or stop renewals. Never delete trial claims, subscriptions, events, grants or customer records as rollback.

If the gate migration needs to be reverted on a disposable rehearsal, disable policy first, restore the previous billing_api_entitlement definition, remove only its two audit triggers and gate-check trigger, then the release-check, audit and customer-launch helper functions and gate table. Verify all preexisting farm/subscription data matches the saved baseline. Production rollback should retain the additive gate schema and move forward with corrected code.

Monitor failed webhook deliveries and reconciliation runs, upcoming grant/reviewer expiry, stale snapshots, duplicate-provider-subscription alerts, payment failures and cancellation outbox failures. The application rejects multiple nonterminal provider subscriptions instead of silently choosing one. The operator should investigate without resetting trial claims or manually fabricating paid snapshots.

## App Review notes draft

BinFlow provides shared grain-operation tools to a farm's authorized users. A farm administrator manages one monthly ($29.99) or annual ($299.99) subscription for the whole farm, with a 30-day free trial for eligible farms. Employees never purchase separately. The coordinated paid launch follows iOS 1.1 approval; no customer-facing payment UI is exposed beforehand. Disclose that launch gate to App Review and agree on any reviewer demonstration needed before approval. For the United States App Store storefront, the administrator can open the secure website in the system browser, select a plan and complete Stripe Checkout. A short-lived one-use handoff preserves the existing farm without transferring login tokens. The app checks server entitlement on return; the return page alone grants no access. Other or unknown storefronts have no external purchase button. Purchasing is not implemented through a native payment sheet.

Supply the dedicated reviewer login and farm privately in App Review Information, with a preapproved valid access grant and sample records so no payment is necessary. Provide a separate eligible test login if Apple requests onboarding review. Explain Safari return and the status refresh action. Never put passwords or signing material in these notes in Git. Approval remains Apple's decision under the applicable storefront rules.
